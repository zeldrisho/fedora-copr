# REA

`rea` is a reverse engineering CLI and MCP server. Run `rea setup` to review agent configuration changes; use RPM updates rather than `rea update`. Setup modifies user configuration only after approval. REA executes analysis tools with the user's privileges; inspect untrusted targets in an appropriate isolation environment. Ghidra and other analysis engines are separately installed and configured. Linux process ownership checks require `procps-ng`.

## Sources and build

- [Upstream installation](https://github.com/morluto/rea/blob/rea-agents-6.9.0/docs/getting-started/installation.md) recommends the published npm package. [Upstream release documentation](https://github.com/morluto/rea/blob/rea-agents-6.9.0/docs/development/releasing.md) describes testing the exact npm archive.
- The [Fedora Node.js guidelines](https://docs.fedoraproject.org/en-US/packaging-guidelines/Node.js/) prefer npm registry tarballs and require bundled license review. The npm archive contains generated JavaScript rather than TypeScript source; this personal COPR ships those upstream-generated files rather than rebuilding them. The [tagged repository](https://github.com/morluto/rea/tree/rea-agents-6.9.0) contains the corresponding source.
- The [AUR package](https://aur.archlinux.org/packages/rea-agents) exists, but its recipe was inaccessible behind an anti-bot challenge during research. No Fedora or COPR recipe was identified; this is not a definitive availability claim.

SRPM preparation checks `checksums.sha256`. RPM builds need network access to install the shrinkwrap's integrity-pinned npm dependencies and to build the pinned OpenPGP.js source, with lifecycle scripts disabled; no dependency cache is bundled in the SRPM. Packit PR and main jobs are network-enabled. Only the `rea` command is installed, not its upstream `rea-agents` alias. Review upstream changes, dependencies, integrity pins, and applicable notices when updating.

The runtime includes upstream prebuilt `@lydell/node-pty` binaries and WASM from dependencies. These have not been independently rebuilt or audited. Frida is removed because its native binding requires an install step; Frida functionality is unavailable in this package. The npm tarball's Windows native binary is not installed. The runtime license inventory is generated from npm metadata and needs independent review, including shipped third-party notices. External engines and optional tools can have additional licensing and security requirements. Desktop-build integration invokes `python3`, and Hopper provisioning invokes `tar`; these optional features have further prerequisites that REA's doctor checks, so they are not required by the base RPM. The `sqlite` build dependency supplies the test fixture command; REA uses Node's SQLite support for that check.

## Updates and limitations

The 6.9.0 shrinkwrap pins `openpgp` 6.3.2, which is LGPL-3.0-or-later. Its [npm archive](https://registry.npmjs.org/openpgp/-/openpgp-6.3.2.tgz) ships generated `dist` files and an LGPL license, not its source tree. The spec therefore adds the checksummed [v6.3.2 source tag](https://github.com/openpgpjs/openpgpjs/tree/v6.3.2) as `Source2`, builds it during `%build` with its committed `package-lock.json` and [Rollup configuration](https://github.com/openpgpjs/openpgpjs/blob/v6.3.2/rollup.config.js), and installs that build instead of the npm bundle. The SRPM carries the corresponding source and build inputs alongside the unmodified upstream npm archive; the binary RPM installs the built OpenPGP.js files, license and README, not the source tree. The GitHub archive is checksum-pinned in `checksums.sha256`; if GitHub regenerates it, source preparation fails until the new checksum is reviewed. A local rebuild produced the same file layout as the npm archive, including the minified-bundle maps with embedded `sourcesContent`, but not byte-identical output; it is not a provenance proof for upstream's published files. REA imports `openpgp` dynamically from `dist/process/DetachedPgpSignature.js`, the bundled CLI and the MCP Hopper implementation; `%check` exercises a sign/verify round trip against the installed build and still verifies the embedded source maps. The spec carries a `# livecheck: manual` marker: every update must re-check the OpenPGP.js pin, its checksum and the Node.js range.

The Rawhide x86_64 RPM from PR #2 also has an automatically generated `/usr/bin/node` requirement from executable Node shebangs, in addition to the explicit `nodejs24` requirement. Fedora 45's `nodejs24` itself requires `/usr/bin/node`, so filtering REA's dependency alone would not avoid that provider. Verify which bundled scripts are executed directly and which Node version they use before changing this metadata.

REA uses OpenPGP.js to verify signed Hopper releases before provisioning. The checksummed upstream npm archive itself contains `package/node_modules/openpgp`; the spec leaves that archive unmodified in the SRPM and replaces only the installed copy with the build from `Source2`, so Hopper provisioning keeps its signature verification. Do not bypass that verification or drop the dependency without an equivalent reviewed implementation.

## Validation

Upstream 6.9.0 accepts Node.js `^22.23.4 || ^24.22.1 || >=26.12.1`. The RPM specifically requires Fedora's `nodejs24` >= `1:24.22.1` and invokes `/usr/bin/node-24`, avoiding an incompatible default Node stream. COPR build 11322134 confirmed that the required Node version was unavailable in stable Fedora 44 and 45; do not lower the requirement below upstream's supported range. Stable Fedora 44 and 45 currently provide `nodejs24` 24.18.0 and `nodejs22` 22.23.1, while Rawhide provides 24.22.1 and Fedora 44/45 `updates-testing` provide 24.22.1-3. Packit builds rea only on the Rawhide chroots until the update reaches stable; re-add `fedora-44-x86_64`, `fedora-44-aarch64`, `fedora-45-x86_64` and `fedora-45-aarch64` to both rea jobs in `.packit.yaml` afterwards, and recheck the enabled repositories before relying on published packages. Rawhide reached RPM packaging but failed on an empty debugsource package for prebuilt binaries; the spec disables debugsource generation for those inputs and this rebuild still needs verification. The RPM has not been built successfully on Fedora or validated on either architecture. A local offline npm install, CLI startup, and small JavaScript analysis were checked on macOS, not Fedora, and a local OpenPGP.js source build and sign/verify round trip were checked on Linux, not inside an RPM build. These do not verify MCP sessions, setup, Linux native PTY behavior, or external analysis engines.

A downstream relaxation to Node.js 24.18.0 was considered and rejected. REA enforces the range at runtime, so it would need `engines.node` plus the range and remediation strings in `dist/domain/runtimeVersion.js`, `dist/cli-runtime/cliOutput-*.js` and `dist/mcp/runtimeVersion-*.js` rewritten; two of those filenames are content-hashed, so a static patch would break on every release, and the result would claim support for a runtime upstream did not test. With the gate relaxed, a local smoke run on the official Node.js v24.18.0 build passed version, help, doctor, PTY, JavaScript analysis, SQLite inspection, OpenPGP sign/verify and V8 code-cache inspection, but that does not cover MCP, Hopper or Electron paths. The `updates-testing` build of `nodejs24-24.22.1-3` was submitted on 2026-11-02; recheck both stable releases before relying on the package.
