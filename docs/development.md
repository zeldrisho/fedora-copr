# Package development

This guide describes how to maintain packages in this repository. For local setup and commands, see the [toolchain guide](toolchain.md). Consult the [Fedora packaging references](packaging-guidelines/README.md) and [package-maintainer references](package-maintainers/README.md) for Fedora guidance relevant to the package being changed.

## Repository layout

```text
.copr/                  Shared SRPM preparation and COPR project metadata
.github/workflows/      Validation and manual COPR publishing
packages/<name>/        Fedora spec and package-specific sources/docs
scripts/                Repository validation helpers
tests/                  Python tests for repository helpers
docs/                   Shared development, packaging, and Fedora guidance
```

GitHub Actions validates relevant pull requests and pushes to `main`: it runs repository tests, checks package EVR increases, verifies source-checksum manifests for all packages, and validates/lints package SRPMs. The Yazi filter helper's Cargo tests run when that helper changes. PRs receive no COPR credentials and do not submit builds. COPR builds are submitted manually through the `COPR publish` workflow (Run workflow) or local `copr-cli`, never automatically on merge; COPR's configured chroots perform binary builds asynchronously. The workflow uses `ubuntu-latest` and `fedora:latest`; a weekly/manual upstream check reports newer stable releases as issues but never updates packages automatically. Documentation-only changes do not trigger CI. A green PR does not prove that binary RPMs build or work: review COPR build results after publishing and inspect/smoke-test binary packages as described in the toolchain guide.

Every package lives in `packages/<name>/` and uses `packages/<name>/<name>.spec`; the directory, spec basename, and RPM `Name:` must match. Keep specs Fedora-submittable and COPR-specific behavior in `.copr/Makefile`. Package source archives live alongside the spec; their `Source` declarations show how builds consume them. Before changing an archive, read that package's `README.md` and relevant `docs/` notes for provenance and regeneration steps, then verify the package's `docs/checksums.sha256` manifest after the change. For example, see [actionlint's package notes](../packages/actionlint/README.md), [Herdr's notes](../packages/herdr/README.md), and [Yazi's notes](../packages/yazi/README.md). For Fedora review submissions, publish the matching SRPM at a public, directly downloadable URL and include that URL in Bugzilla; the SRPM contains the spec and required source archives for the reviewer.

## Updating a package

1. Review the upstream release, source integrity (including upstream signatures when available), Fedora-allowed licensing, dependencies, and Fedora compatibility. See the [Fedora packaging references](packaging-guidelines/README.md).
2. Update `Version`, source declarations, patches, build requirements, and package documentation as needed. Regenerate checked-in vendored sources when required and keep them synchronized with the spec.
3. Use explicit `Version` and `Release` fields with a maintained `%changelog`; this repository's COPR SRPM flow does not process `%autorelease` or `%autochangelog`. rpmautospec cannot work in this monorepo: it opens the git repository at the spec's own directory without searching parents, so for `packages/<name>/` it finds no history and would always produce Release 1 and a generic changelog entry. Sign changelog entries as `Zeldris Ho <zeldrisho@proton.me>`. Fedora recommends `%autochangelog` (manual changelogs are allowed), so switch to `%autorelease` and `%autochangelog` when the package moves to Fedora dist-git, where the first commit message becomes the initial changelog entry.
4. Ensure all sources are available when creating the SRPM. Binary RPM builds must work offline; do not fetch sources or Go modules during build or test phases. Keep `%check` deterministic and offline. Document and narrowly skip tests that require network access or unavailable release metadata.
5. For changes to an existing package that users would notice (version, installed files, metadata, dependencies, build flags, patches or other sources), increment `Release` and add a changelog entry. Do not bump for packager-only changes: edits confined to comments, `%check`, or `%changelog`, documentation, or COPR configuration. The EVR checker ignores package README files and files under package `docs/` directories; those documentation-only changes do not require an EVR bump. It skips a spec-only change when everything outside comments, `%check` and `%changelog` is unchanged, and ignores individual `BuildRequires` lines immediately preceded by a `# packager-only: BuildRequires` comment (use this only for test/check dependencies that cannot affect the packaged binary). It also ignores deletion of a checked-in archive when the spec declares that exact archive as a remote `Source` (the archive is only a local download cache); modifications and additions to source archives still require an EVR increase. To correct an initial release without bumping, keep `Release: 1` only if all prior COPR builds have been withdrawn and confirmed not downloaded or installed, and add the exact `Initial release reset: all prior COPR builds withdrawn and confirmed not downloaded or installed` changelog line in that change; the checker accepts it only for the same `Version` and only when the line is new, and it can be removed afterward.
6. Run `make validate`, then build and review a binary RPM as described in the [toolchain guide](toolchain.md). Lint the SRPM and every binary RPM; inspect metadata, dependencies, provides, files, and license files; and smoke-test an installed command where practical. `make validate` does not perform binary RPM checks and removes its temporary artifacts when it exits. To retain an SRPM or build outputs, use the persistent-output commands in the [toolchain guide](toolchain.md).

Pull-request CI checks that RPM considers the new Version-Release greater than the merge-base value. The checker permits a reset to Release 1 for the same Version only when the current spec contains the exact initial-release reset marker above and the base spec does not, so the marker authorizes a single reset, documenting that all earlier COPR builds were withdrawn and confirmed not downloaded or installed. Never reuse a version-release that has been published with different package contents.

## Build and publish

Publish manually (see COPR setup), then inspect the COPR build across its configured chroots; the local CI build does not replace those target builds. See [COPR setup](copr.md) for publishing details.

For submission to the official Fedora repositories, follow the [submission guide](submission.md) and use the [review template](templates/review.md). Keep package-specific review records under `packages/<name>/docs/`. COPR publication alone does not submit a Fedora package review.
